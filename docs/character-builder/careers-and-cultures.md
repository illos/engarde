the **inciting-incident** mechanism, and the **culture composite**
(`src/models/culture.ts`, `src/data/culture-data.ts`, `src/enums/culture-type.ts`).

Section references below (`§2`, `§5.1`, `§8.3`) are **ordinal**: `§1` is

`§5` *Choice-point inventory*, `§6` *UI surface*, `§7` *Convex data model notes*,
`§8` *Anomalies & open questions*.

Read [`00-foundation.md`](00-foundation.md) first — it defines the `Feature`
vocabulary, the definition/selection split, and the wizard order that this file
conforms to. Career and culture are steps 3 and 2 of that order.

**There is no "background" build step in Draw Steel** (the rulebook's
Background chapter is narrative framing). Ancestry, culture and career are
three separate, independently-selected build steps. See §8.1 for the source's
`HeroOverview.background` field, which is a display-only concatenation.

## Identity

### `Career` — `src/models/career.ts`

```ts
export interface Career extends Element {
	features: Feature[];
	incitingIncidents: {
		options: Element[];
		selected: Element | null;
	};
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | `string` | From `Element`. Hand-authored, e.g. `career-agent`. |
| `name` | `string` | From `Element`. |
| `description` | `string` | From `Element`. One-line flavour. `text: VERIFY-AGAINST-PIN` |
| `features` | `Feature[]` | Flat, **unlevelled** list. 4–6 entries per career. |
| `incitingIncidents.options` | `Element[]` | Exactly 6 per career in all 18. Career-scoped; no shared pool. |
| `incitingIncidents.selected` | `Element \| null` | The player's single pick. Stored as a **deep copy of the whole option**, not an id. |

Careers have **no level dimension**: no `featuresByLevel`, no `level` field, no
echelon gating. `FeatureLogic.getFeaturesFromCareer` passes `level: undefined`
for every feature. §2 therefore gives **one feature table per career** instead of
a levels 1–10 progression.

Careers also have **no `ancestryPoints`-style budget**, no subclass analogue, and
grant **no abilities directly** (see §4).

### `Culture` — `src/models/culture.ts`

```ts
export interface Culture extends Element {
	type: CultureType;
	language: FeatureLanguageChoice;
	environment: Feature | null;
	organization: Feature | null;
	upbringing: Feature | null;
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | `string` | Generated by `FactoryLogic.createCulture` as `` `culture-${name.replace(' ', '-').toLowerCase()}` ``, or a GUID if `name` is empty. **`replace`, not `replaceAll`** — see §8.6. |
| `name` | `string` | Editable free text for a Bespoke culture; fixed for presets. |
| `description` | `string` | `text: VERIFY-AGAINST-PIN` |
| `type` | `CultureType` | `Bespoke \| Ancestral \| Professional \| Regional`. |
| `language` | `FeatureLanguageChoice` | **Not nullable.** Always present, always a `LanguageChoice` feature. May arrive pre-filled. |
| `environment` | `Feature \| null` | One of 5 fixed `EnvironmentData` features, or null. |
| `organization` | `Feature \| null` | One of 2 fixed `OrganizationData` features, or null. |
| `upbringing` | `Feature \| null` | One of 6 fixed `UpbringingData` features, or null. |

Note the asymmetry: the three axes are **nullable slots holding whole `Feature`
objects**, not `FeatureChoice` features with an `options` list. The "which
environment?" decision is therefore **not** expressible in the `Feature`
vocabulary at all — it lives in bespoke code and bespoke UI. This is the single
most important structural fact in this file for our data model (§7, §8.3).

### `CultureType` — `src/enums/culture-type.ts`

| Value | Meaning in the source | Where instances live at `01672c1` |
|---|---|---|
| `Bespoke` | The three axes are **unset** and the player chooses each. Name is player-authored. | Exactly one: `CultureData.bespoke`. |
| `Ancestral` | A preset attached to an `Ancestry` (`Ancestry.culture?`). All three axes **and** a language pre-filled. | 11 of the 12 official ancestries; plus community ancestries. |
| `Professional` | A preset in a sourcebook's `cultures[]`. All three axes pre-filled; **no** language pre-fill. | 16, all in official `core`. |
| `Regional` | A preset in a sourcebook's `cultures[]`, with a language pre-fill. | 0 official; 23 in the community `age-of-secrets` sourcebook. Out of V1 scope. |

## Level progression

**Not applicable in the source's sense** — careers and cultures carry no
`featuresByLevel`. Per the brief, this section is one feature table per career,
using the standard columns with `Level` fixed at `—`.

### How to read these tables

Every career feature is produced by one of four `FactoryLogic.feature.create*`
builders. The **defaults each builder applies** (resolved from
`src/logic/factory-feature-logic.ts`) are load-bearing — a call with no `count`
is not "no count":

| Builder | `FeatureType` | Defaults applied when the field is omitted |
|---|---|---|
| `createSkillChoice` | `SkillChoice` | `count: 1`, `options: []`, `listOptions: []`, `selectAt: 'build'`, `selected: []`. **If `options` *and* `listOptions` are both empty, `listOptions` is replaced with all five lists** `[Crafting, Exploration, Interpersonal, Intrigue, Lore]` — i.e. "choose any skill". `name` defaults to `` `${prefix}Skill` `` / `` `${prefix}Skills` `` where `prefix` is the `' / '`-joined `listOptions` **only when** `options` is empty and `listOptions.length < 5`. |
| `createLanguageChoice` | `LanguageChoice` | `count: 1`, `options: []`, `allowedTypes: [Common, Regional, Cultural, Dead]` (all four; `Custom` excluded), `selectAt: 'build'`, `selected: []`. `name` defaults to `'Language'` (count 1) or `'Languages'`. |
| `createPerk` | `Perk` | `count: 1`, `selected: []`; `lists` defaults to `[Crafting, Exploration, Interpersonal, Intrigue, Lore, Supernatural]` — **`PerkList.Special` is excluded from the default**. `name` defaults to `` `${lists.join(' / ')} Perk` ``. |
| `createBonus` | `Bonus` | `value: 0`, `valueFromController: null`, `valueCharacteristics: []`, `valueCharacteristicMultiplier: 1`, `valuePerLevel: 0`, `valuePerEchelon: 0`. `name` defaults to `field.toString()`. |

`Name` in the tables below is the **derived** name (no career passes an explicit
`name`). `Option source` describes the pool the control resolves against.
`Selection shape` is what lands in `feature.data.selected`.

Two option pools are global, not career-local:

- **Skills** — `SourcebookLogic.getSkills(sourcebooks)`, filtered to
  `options.includes(name) || listOptions.includes(skill.list)`, then filtered to
  exclude skills the hero already has and skills the hero has had cancelled.
  Official `core` defines **56 skills** across the 5 lists.
- **Languages** — `SourcebookLogic.getLanguages(sourcebooks)`, filtered by
  `allowedTypes` and de-duplicated against languages the hero already knows.
  Official `core` defines **zero** languages; all 42 official languages live in
  the separate **`orden`** sourcebook. See §8.7.
- **Perks** — `SourcebookLogic.getPerks(sourcebooks)` filtered by `lists`.
  47 perks: Crafting 6, Exploration 10, Interpersonal 10, Intrigue 6, Lore 8,
  Supernatural 7. No `Special` perks exist at this commit.

### 2.20 The inciting incident

`incitingIncidents` is **not** a `Feature`. It is a career-scoped sibling of
`features`, with its own model shape, its own UI control, and its own persistence
path. Precisely:

| Property | Value |
|---|---|
| Cardinality | **single-select, exactly 1 of 6**, required |
| Option scope | **Career-local.** Each career carries its own six `Element`s; there is no shared pool and no cross-career reuse (two careers both have an incident named "Betrayed" — Gladiator's `career-gladiator-ii-1` and Warden's `career-warden-ii-1` — but they are distinct ids with distinct text). |
| Option shape | `Element { id, name, description }`. `description` is prose — `text: VERIFY-AGAINST-PIN` |
| Stored as | `incitingIncidents.selected: Element \| null` — a **deep copy of the whole option object** (`Utils.copy`), not an id reference |
| Mechanical effect | **None found in the source.** No skill, bonus, language or perk is attached. It is narrative-only, surfaced on the hero sheet (`hero-sheet-builder.ts` → `sheet.incitingIncident`) and in the overview string. |
| Clearable | Yes — `selectIncitingIncident(null)` |
| Completion gate | The career wizard step reports `Completed` only when every choice feature is chosen **and** `incitingIncidents.selected !== null` |
| Randomiser | `HeroLogic` random-hero generation draws one uniformly (`Collections.draw`) |
| Portable form | `Pregen.incitingIncidentID: string \| null` — the source **already** projects it to a bare id for its pregen format. That is the shape we should store. |

## Abilities

**Careers and cultures grant no abilities directly.** No career feature is
`FeatureType.Ability`, `AbilityCost`, `AbilityDamage`, `AbilityDistance` or
`AbilityKeyword`; neither is any culture axis. All 84 career features are
`SkillChoice` / `LanguageChoice` / `Bonus` / `Perk`; all 13 culture axis features
are `SkillChoice`; the culture language slot is `LanguageChoice`.

**Abilities can still arrive via a career, indirectly, through the perk.** A
`Perk` is itself a `Feature` (`Perk = Feature & { list: PerkList }`), and
`FeatureLogic.simplifyFeatures` flattens each selected perk into the hero's
feature list. Several perks are `FeatureType.Ability` — e.g. two of the ten
Exploration perks and four of the seven Supernatural perks. So choosing
Disciple → Supernatural Perk → *an Ability perk* is a path from a career to an
ability. Ability-level detail belongs to `complications-titles-perks.md`, not
here; the structural point for this file is that **the career's perk slot is a
gateway into the ability system**, so career selection cannot be modelled as
"skills, languages and flat numbers only".

### 5.5 Cross-step interaction: de-duplication

Selecting a career (or a culture, ancestry, class or complication) runs
`clearRedundantSelections` over the **incoming** element's features:

- `LanguageChoice.selected` is filtered to drop languages the hero already knows.
- `SkillChoice.selected` is filtered to drop skills the hero already has **or has
  had cancelled** (cancelled skills count as known forever).

This is how the 11 pre-seeded career skills degrade gracefully: pick Agent when
you already have Sneak and the pre-seed is stripped, leaving `career-agent-feature-1`
as an open "choose any skill" control. In addition, `ConfigSkillChoice` filters
the *option list* against already-known skills, and flags a live duplicate with a
`Duplicated` warning if one slips through.

**Consequence for us:** a career's contribution is not a pure function of the
career id. It depends on what the hero already knows at the moment the career is
attached — and it is applied **destructively, once, at attach time**, not
re-derived. Two heroes with the same career id can have different open choices.

## Convex data model notes

> **Superseded keying note (2026-08-30):** the FS-id keys sketched in this
> section are illustrative only and are **superseded** by `00-foundation.md`
> §6b + ruling R-L: every persistent key joins on the pin's `scc` identity
> (with a discriminator where one pin record carries several choice points).
> FS ids are labels, never keys.


### 7.1 Definition data (seeded, shared, versioned by source)

```ts
// careers
careers: {
  sourceId, careerId,            // 'core' / 'career-agent'
  name, description,
  features: FeatureDef[],        // 4-6, unlevelled
  incitingIncidents: { incidentId, name, description }[]   // exactly 6
}

// culture axes — one shared table, three kinds
cultureAxes: {
  sourceId, axisId,              // 'env-nomadic' | 'org-communal' | 'up-martial'
  axis: 'environment' | 'organization' | 'upbringing',
  name, description,
  skillChoice: { options: string[], listOptions: SkillList[], count: 1 }
}

// preset cultures
cultures: {
  sourceId, cultureId, name, description,
  type: 'ancestral' | 'professional' | 'regional',
  environmentAxisId, organizationAxisId, upbringingAxisId,   // nullable
  presetLanguage: string | null,
  ancestryId: string | null      // set for Ancestral cultures owned by an ancestry
}
```

Three notes on this shape:

- **Do not model the culture axes as `null`able embedded `Feature`s.** Model them
  as a first-class `cultureAxes` table with an `axis` discriminator, and have
  both preset cultures and hero selections reference axis **ids**. This removes
  the source's biggest structural wart in one move (§8.3).
- **`Bespoke` is not a row.** It is the *absence* of a `cultureId` plus a
  hero-authored name. Do not seed a `culture-bespoke-culture` row and then
  special-case its id everywhere, which is what the source does.
- **Ancestral cultures are owned by ancestries** (`Ancestry.culture?`), and are
  surfaced to the culture picker only because `getCultures(..., includeFromAncestries: true)`
  splices them in. Seed them into `cultures` with an `ancestryId` back-reference
  so the *Your Ancestry* group is a query, not a splice.

### 7.2 Selection state (per hero, sparse)

```ts
heroes: {
  // ...
  careerId: string | null,
  incitingIncidentId: string | null,

  cultureId: string | null,              // null + cultureName set => bespoke
  cultureName: string | null,            // bespoke only
  cultureEnvironmentAxisId: string | null,
  cultureOrganizationAxisId: string | null,
  cultureUpbringingAxisId: string | null,

  selections: Record<featureId, string[]>   // sparse; skill/language names, perk ids
}
```

The source itself proves this projection works: `Pregen`
(`src/models/pregen.ts`) is exactly it —

```ts
cultureID, careerID, incitingIncidentID: string | null;
featureSelections: { featureID: string; selections: string[] }[];
```

`PregenLogic.getFeatureSelections` / `setFeatureSelections` are the round-trip.
Note the payload heterogeneity: `SkillChoice` and `LanguageChoice` project to
**names**, everything else (`Perk`, `Choice`, `Domain`, …) projects to **ids**.
We should normalise — skills and languages should be id-keyed in our seed data
so `selections` is uniformly `string[]` of ids.

Also note what `Pregen` **loses**: a bespoke culture's player-authored *name*.
It stores only `cultureID` (`culture-bespoke-culture`), so a round-tripped
bespoke hero reverts to the name "Bespoke Culture". Our model must carry the name
explicitly (`cultureName` above).

### 7.3 Where the definition/selection split is hard here

1. **The three culture axes are not choice features.** In the source the axis
   *is* the slot; picking Nomadic writes a whole `Feature` object into
   `culture.environment`. There is no feature id whose `selected` field records
   "the player chose Nomadic". `PregenLogic` works around this by **prefix-matching
   feature ids** — it scans `featureSelections` for an id starting with `env-` /
   `org-` / `up-` to recover which axis was chosen. That is a string-prefix hack
   standing in for a missing relationship. **Fix it in our model** with the three
   explicit `culture*AxisId` fields above (§7.2), and keep `selections` for the
   skill each axis then asks for.

2. **Two-level dependent choice.** Environment → environment's skill list →
   skill. Change the environment and the previously chosen skill may no longer be
   legal. `PregenLogic.pregenToHero` deals with this by **looping until fixed
   point** (`while (features.length > 0)`), re-querying which choice features are
   now visible-and-unanswered after each pass. Our resolver needs the same
   fixed-point discipline, and the UI needs downstream invalidation on upstream
   change.

3. **De-duplication is destructive and order-dependent** (§5.5). The source
   mutates the incoming element's `selected` arrays at attach time. In a sparse
   model, the equivalent must be **derivation-time**, not write-time: keep the
   raw selection, and have the resolver report a duplicate as a validation
   warning. Otherwise reordering the wizard steps silently changes the hero.
   This also means **career pre-seeds must be modelled as defaults, not as
   selections** — `defaultSelection: ['Sneak']` in the definition, materialised
   into `selections` only if legal at the time the career is attached.

4. **Perk selections nest.** A `Perk` is a `Feature`; a chosen perk is flattened
   into the hero's feature list and may carry its own choice features (Linguist →
   2 languages). So `selections` keys include ids that only exist **because of**
   another selection. Our key convention must handle "feature id reachable only
   through a selected feature", which is the same problem `00-foundation.md` §6
   flags for `Multiple` / `Package` / `Toggle`.

5. **The synthetic culture-lore feature has a name-derived id** (§5.3). Any
   id-keyed store must not use it as a key. Give it a stable id derived from
   `cultureId` (or from `'bespoke'`), never from the display name.

6. **`Perk.selected` stores whole `Perk` objects**, `SkillChoice.selected` stores
   name strings, `incitingIncidents.selected` stores a whole `Element`. Three
   different reference disciplines for three adjacent controls. Normalise to ids.

7. **Cross-source option pools.** A career's language control resolves against
   `sourcebook.languages`, and **official `core` has none** — the 42 official
   languages live in `orden`. A hero with `core` enabled and `orden` disabled has
   16 careers with unanswerable language controls. Our seed must either move
   languages into the same source as the careers, or the resolver must report
   "no legal options for this control" as a first-class state rather than an
   empty drawer.

8. **`selectAt` is uniformly `'build'`** for every career and culture feature at
   this commit. Careers and cultures therefore do **not** exercise the
   respite/play write path that `00-foundation.md` §6 flags — but the field is
   present on every `SkillChoice` / `LanguageChoice` we seed, so the schema
   should still carry it.

## Anomalies & open questions

### 8.1 `HeroOverview.background` is a display-only concatenation

There is no "background" mechanic in Draw Steel, and the source does not model one.
`HeroOverview.background: string | null` is built by `HeroLogic.createOverview`
as a comma-joined string of **culture name** (omitted when the culture is
Bespoke) + **career name** + **inciting incident name**. It is consumed in
exactly two places: a `Field label='Background'` on the hero-overview panel, and
the hero-list search index. **It is presentation, not data.** Do not put a
`background` field on our hero document; if we want that summary line, compute it.

### 8.2 Fixed career skills are modelled as fully-open choices with a pre-seed

Eleven careers grant a specific named skill (Agent→Sneak, Beggar→Rumors,
Criminal→Criminal Underworld, Disciple→Religion, Explorer→Navigate,
Farmer→Handle Animals, Laborer→Endurance, Mage's Apprentice→Magic, Sailor→Swim,
Warden→Nature, Watch Officer→Alertness). Every one is authored as
`createSkillChoice({ id, selected: ['X'] })` with **no `options` and no
`listOptions`** — which the builder's fallback turns into "choose any skill from
any of the five lists", pre-filled with X.

So in the source a player can freely swap Agent's Sneak for Alchemy. That is
either (a) a deliberate affordance, (b) a compact way to express "you get X, but
if you already have X, choose anything", or (c) a transcription shortcut. The
de-duplication logic (§5.5) suggests (b). **This must be resolved against the
pin before implementation** — it is the difference between a granted skill and a
free skill choice, and it affects 11 of 18 careers.

### 8.3 The culture composite is not expressible in the `Feature` vocabulary

`environment` / `organization` / `upbringing` are `Feature | null` slots, not
`FeatureChoice` features. Consequences visible in the source:

- The three pickers are hand-written in `culture-section.tsx` rather than being
  produced by the generic `ConfigFeature` renderer.
- `PregenLogic` recovers the chosen axes by **prefix-matching `env-` / `org-` /
  `up-` against feature ids** (§7.3.1).
- `getFeaturesFromCulture` has to null-check each slot individually.
- The axes have no "unchosen" representation distinct from "this culture has no
  organization" — see 8.9.

Fix in our model; do not port the shape.

### 8.4 Two careers have no language choice

Disciple and Performer grant zero languages. Every other career grants 1 or 2.
Flagged because it is the kind of asymmetry that reads as a transcription
omission — **verify against the pin**.

### 8.5 Four careers use inconsistent feature-id prefixes

Gladiator, Laborer, Mage's Apprentice and Performer author their feature ids as
`gladiator-feature-1`, `laborer-feature-1`, `mages-apprentice-feature-1`,
`performer-feature-1` — **without** the `career-` prefix the other fourteen use.
Their *inciting incident* ids do carry the prefix (`career-gladiator-ii-1`), so
the inconsistency is limited to `features[]`.

This is exactly the id-stability hazard `00-foundation.md` §8.3 raises. If we
seed feature ids verbatim from Forge Steel we inherit a namespace where
`laborer-feature-1` and some future non-career `laborer-*` element could collide.
**Recommendation: mint our own ids** (`<sourceId>:<careerId>:<n>`) with a
recorded mapping to Forge Steel's, rather than adopting theirs.

### 8.6 Culture id generation uses `replace`, not `replaceAll`

`FactoryLogic.createCulture` builds `` `culture-${name.replace(' ', '-').toLowerCase()}` ``.
`String.replace` with a string argument replaces **only the first occurrence**.
No culture at this commit has a three-word name, so nothing collides today — but
"Borderland Homestead Two" would produce `culture-borderland-homestead two`, with
a literal space in the id. Latent, not live.

Separately, the synthetic culture-lore feature (§5.3) uses `replaceAll` for the
same job — two different id-slug rules in the same subsystem.

### 8.7 Career language controls depend on a sourcebook the careers are not in

Official `core` declares `languages: []`. All 42 official languages are in the
separate `orden` sourcebook. Sixteen careers, plus every culture, have a
`LanguageChoice`. A hero whose enabled sources are `core`-only gets a language
drawer with nothing in it and no explanation. See §7.3.7.

Open question for us: **is `orden` in V1's source set?** `00-foundation.md` §8.1
lists our pin as core + Beastheart; languages are not in either.

### 8.8 Preset cultures are not re-editable in the builder

The environment/organization/upbringing pickers render **only** when
`culture.id === CultureData.bespoke.id`. Choose "Noble House" and you get its
three axes fixed, with only the language and the three axis *skills* left to
choose. There is no "start from this preset and tweak it" path — you must switch
to Bespoke and rebuild all three. Worth a product decision; the affordance is
cheap for us and the source's omission looks incidental rather than principled.

### 8.9 A preset culture may leave an axis null

`FactoryLogic.createCulture`'s axis parameters are optional. At least one
community culture ("Icewell", `age-of-secrets`) passes `undefined` for
`upbringing`, describing itself as "(any upbringing)". But because the axis
pickers only render for Bespoke, **that culture's upbringing can never be
chosen** — it is permanently null and the hero silently loses an upbringing skill.
A structural dead end. Our model should distinguish
`axisId: null /* unset, player chooses */` from `axis: 'none' /* culture has none */`,
and render a picker for the former regardless of culture type.

### 8.10 `CultureType.Regional` has no UI group

Enumerated, used by community content, and rendered by none of the culture
picker's four groups (§5.1). Dead branch at this commit for anything that is not
also an ancestry's own culture.

### 8.11 Only 11 of 12 official ancestries carry a culture

Devil, Dragon Knight, Dwarf, High Elf, Wode Elf, Hakaan, Human, Memonek, Orc,
Polder and Time Raider each carry an `Ancestral` culture. **Revenant does not.**
So a Revenant hero has an empty *Your Ancestry* group. Verify against the pin
whether that is correct or a transcription gap. (Ancestry detail belongs to
`ancestries.md`; recorded here because it is a culture-picker input.)

### 8.12 Inciting incidents have no mechanical effect

Searched: no career's incident carries a feature, bonus, skill or ability. It is
narrative-only. If the pin says otherwise for any of the 108, our `Element`-shaped
option row will need to grow a `features` array.

### 8.13 Career/culture prose was deliberately not transcribed

Per the brief's hard constraint 2, no career description, no inciting-incident
description, no axis description and no culture description text appears in this
file. Every one is marked `text: VERIFY-AGAINST-PIN`. Total prose fields that a
canon pass must supply: 18 career descriptions + 108 inciting-incident
descriptions + 13 culture-axis descriptions + 1 synthetic culture-lore text
+ N preset-culture descriptions = **140 + N**.

### 8.14 Unresolved from the source

- Whether a career's pre-seeded skill is a grant or a default (§8.2). Highest-value
  question in this file — affects 11 careers.
- Whether the "any skill from any list" fallback is intended semantics or an
  artifact of the builder's default (§8.2 is the same question from the other side).
- Whether the ×2 `Renown` careers (Gladiator, Performer) and ×1 `Renown` careers
  form a real pattern or a transcription accident.
- Whether `ProjectPoints` 120 vs 240 tracks something (both values appear 4 and 3
  times respectively, and never on the same career as a `Renown` bonus except
  Mage's Apprentice, which has `Renown` and no project points). Not resolvable
  from the source.
- Whether cultures/careers from non-`core` sourcebooks are in V1 scope. The
  `age-of-secrets` community sourcebook adds 5 careers and 23 Regional cultures.
